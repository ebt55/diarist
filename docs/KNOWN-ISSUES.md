# Known issues

Status: 22 Oct 2026, for 0.1.0-beta.4. Kept by hand from the research notes in `docs/research`, the model guide (`docs/04-model-guide.md`), the evaluation notes in `docs/eval` and the changelog. Each row says where the problem sits (upstream in the runtime, in a model, by design, or Diarist's own), what the app does about it today, and what a fix waits on. Rows link to the upstream issue where one exists. Something missing here: [open an issue](https://github.com/ebt55/diarist/issues).

## The runtime (NeMo-Speech.cpp 0.2.0)

| Issue | Affects | Status | What Diarist does meanwhile | Waiting on |
|---|---|---|---|---|
| Plain `transcribe --diarize` tags the wrong speaker on the first minutes of a long file. On a 21-minute AMI meeting about 63 percent of words carried the right speaker; with `--stream --endpointing` 99.6 percent. | The runtime's plain file path, not the one Diarist uses | Upstream, fixed on `main`, not yet released: [NVIDIA/NeMo-Speech.cpp#67](https://github.com/NVIDIA/NeMo-Speech.cpp/issues/67), filed by the author on 15 Oct 2026 and closed on 16 Oct 2026 by [PR #70](https://github.com/NVIDIA/NeMo-Speech.cpp/pull/70) ("keep frames for words not yet tagged": 59.2 to 99.7 percent of words correctly tagged on the 21-minute file). The latest runtime release is still 0.2.0 (2 Oct 2026), so the fix reaches the shipped runtime only with the next release. On 16 Oct 2026 a maintainer reproduced it (plain `--diarize` 59.2 percent of words correctly tagged on the 21-minute file, 23.8 percent in its first five minutes; the streaming path with endpointing 99.7 percent) and gave the cause: after 20 minutes the diarizer keeps only the last ten minutes of frame probabilities, and without endpointing words are tagged only at the end of the file, so `--stream` without `--endpointing` has the same problem while the standalone `diarize` is unaffected | Every file job runs through the streaming path with endpointing (`--stream --endpointing`), which was never affected | A runtime release that carries the fix; the next runtime upgrade re-runs the eval set before the plain path is considered again |
| The WebSocket `commit` message never returns a completion for utterances of about a second or more. | Live recording, if the app relied on `commit` to flush the last words | Upstream, open: [NVIDIA/NeMo-Speech.cpp#49](https://github.com/NVIDIA/NeMo-Speech.cpp/issues/49) | Diarist does not depend on `commit`: endpointing is on, so finals arrive per utterance, and the post-pass after Stop produces the stored transcript | A fix upstream |
| Streaming wedges after sustained all-zero audio. | Live recording while the system audio is exactly silent | Upstream, open: [NVIDIA/NeMo-Speech.cpp#48](https://github.com/NVIDIA/NeMo-Speech.cpp/issues/48) | Frames that are exactly zero get 1-LSB dither before they reach the engine, so the engine never sees sustained digital silence | A fix upstream |
| Word confidence is always 1.0. | Every transcript | Upstream, open: [NVIDIA/NeMo-Speech.cpp#55](https://github.com/NVIDIA/NeMo-Speech.cpp/issues/55) | The UI cannot flag uncertain words yet, and nothing is shown that pretends otherwise | The runtime exposing confidence or token probabilities |
| Speaker labels are never revised over the WebSocket or the C ABI. The revision path the runtime's own command-line tool uses is not exposed to other programs. | Labels in the live view | Upstream limitation; by design in Diarist until it changes | Live labels are provisional. The post-pass after Stop produces the stored transcript, and the names you gave people during the meeting carry over | An upstream API for label revisions |
| The runtime's punctuation hook (`--pnc-model`) never runs for Diarist's speech models. The runtime decides when it loads a model whether the model punctuates by itself, and both Nemotron models count as self-punctuating because their vocabularies contain sentence terminators (`.`, `?`, `!`), so it ignores a punctuation model with a warning before even opening it. Its converter also accepts only NeMo's BERT punctuation model, whose NVIDIA checkpoints cannot be redistributed. | Punctuation and casing of every transcript (see "The Nemotron models punctuate little" below) | Upstream design; measured with NeMo-Speech.cpp 0.2.0 (docs/research/12, section 3) | Nothing yet: lines are split at pauses and speaker changes | Punctuation restoration inside Diarist (a multilingual punctuation model run on the CPU over the finished words, keeping their times), planned, not yet scheduled |
| The runtime's `--verbatim` flag does not bring back filler words. In NeMo-Speech.cpp 0.2.0 it only skips inverse text normalisation, and with no normalisation grammars configured the output is word for word and time for time the same; the model itself leaves the fillers out. | Anyone hoping to keep "um" and "uh" with Nemotron 3.5 | Upstream behaviour, measured (docs/research/12, section 6) | Diarist does not pass it. The EN model keeps fillers | Nothing. Listed so nobody tries it again |
| Model paths of 260 characters or more fail with "model does not exist". The runtime's model layout nests the publisher, the repository and a 40-character revision under the data folder, so a deep data folder reaches the limit. | Imports and live recording with a deep data folder | Upstream limitation, handled | Diarist passes long paths in Windows' extended-length form (the `\\?\` prefix) | Nothing. Listed so it is not investigated twice |

## Diarist itself

| Issue | Affects | Status | What Diarist does meanwhile | Waiting on |
|---|---|---|---|---|
| Recording without headphones: the other participants come out of your speakers and into your microphone, or leak from headphones into a sensitive one. Diarist checks "me" against the other side in three ways: what the other side said a moment before (a run of three or more words repeated with one delay goes, two only with an acoustic check, single words never), how loud the word is (at the microphone's noise floor while the other side talks, and never near your own level), and, when the microphone clearly hears the system audio, the correlation of the two (300 to 3,400 Hz); stray fragments inside a phrase that was echo go with it. In the processing after Stop its own echo canceller first takes the other side out of a temporary copy of the microphone audio (the stored audio stays as recorded), and what is left of a loud echo is judged on the microphone as recorded (the live transcript's "me", or the microphone transcribed once more) and removed where the canceller cut it. Measured on the author's five test recordings: 0 to 0.7 percent of "me" left as copies of the other side after processing (69 of 386 words before on the headphone recording, 2 of 292 now; on the loud speaker recording 21 of 293 before, none now), 0 to 0.8 percent in the live run, where the matcher alone finds 1.7 to 6.4 percent by chance; 98.3 percent or more of the author's own words kept on the 111-minute speaker recording, and on the 21 Oct speaker recordings every word of the author's the canceller left alone but one. What remains: on the headphone recording 7 of 292 words the measurement counts as the author's were removed (garbled leak words at the noise floor, by reading them); the live view decides a word within 3 s of showing it, so the first seconds of a leak can stay visible until Stop removes them; and after the canceller the author's own words spoken over continuous echo look like its residue: the decision on the recorded microphone costs them half a point of word error rate (7.6 to 8.1 percent on the spliced set; stricter settings cost 2 points or more, docs/eval/2026-10-21-echo-round2.md). A weak cancellation of a loud echo can leave echo fragments in "me": on one speaker interview of the author's the canceller took only 7 dB off the echo, and about one word in eight of its "me" was such a fragment (docs/eval/2026-10-26-echo-owner-level.md). An author who speaks close to the microphone's noise floor (their words less than 15 dB over it after the canceller; the run's details record `owner_low`) is near the level of what is left of the echo, and the gate's level checks cannot tell their words from echo at the floor. | Live recording without headphones, and headphones that leak | Diarist's own, measured on one PC and five recordings (docs/eval/2026-10-21-echo-round2.md). Windows' own echo cancellation was measured on that PC and cancelled nothing ([docs/research/14-echo-cancellation.md](research/14-echo-cancellation.md), section 1), so it is not used | Settings, Recording, "Recording with speakers (echo)": Detect and handle (default), Off, Always on, and the gate threshold under Advanced. The live view says when the microphone hears the meeting, with "Turn off for this recording" (N). The meeting details say how many words were removed and why (hover a word in "Show them"), with Restore to put them back as "me" and "Remove echo words again" to undo that. Headphones still give the cleanest "me" | The live canceller (plan 15, chunk B2b); speaker recordings from other PCs; the author's next headphone and speaker recordings |
| When a name you gave during a recording reaches nobody in the final transcript, the live transcript is kept for that meeting (as with the "keep live runs" setting), but nothing shows it yet and nothing cleans it up. | Meetings where a name from the live view could not be placed after Stop (the final transcript shows "Speaker N" for that person) | Diarist's own, since the fix of names given while recording (Unreleased) | The kept live run sits in the database (the final run's details record how many names were not placed); rename the speaker in the final transcript | A banner on the meeting and a "place names" action |
| Within a second of a speaker change, 5.5 to 7.8 percent of words go to the wrong speaker with Nemotron 3.5 and 5.6 to 12.7 with the EN model (0.2 to 0.3 percent overall), measured on the author's Zoom meetings with 0.1.0-beta.2's file setting (7 to 9 percent with 0.1.0-beta.1's). | Lines at speaker changes | Diarist's own, measured. The runtime's word tags are used as they come, with no smoothing yet | Move a line to the right person, or split it | Speaker-change handling, on the roadmap |
| Imports and the processing after Stop can merge a speaker who says very little into another label. On one Zoom meeting a participant with 7 words lost their own label (5 speakers found as 4) with both speech models. It is the cost of the offline diarizer geometry that file jobs use since 0.1.0-beta.2, which elsewhere puts fewer words near speaker changes on the wrong speaker. | Meetings with someone who speaks only a sentence or two | Diarist's own choice, measured on the full evaluation set (docs/eval/2026-10-16-shipped_n35.md and -shipped_en.md); within docs/00's bar of a speaker count within one | Reassign or split the line. To tag file jobs with the streaming geometry, as live recording does, set `engine.file_diar_preset` to `streaming` (docs/04-model-guide.md, section 5) | A diarizer setting that keeps short speakers, or speaker identity across meetings |
| The same person is not recognised across meetings. Every recording starts with fresh labels. | Everyone | Not built yet | Rename the speaker in each meeting | Speaker identity across meetings, on the roadmap |
| Up to 0.1.0-beta.4, imports and recordings failed when the runtime's own path was 260 characters or more: Windows could not start the engine ("path not found", os error 3). The runtime lives under `<data folder>\engine\<package>\bin`, so a deep data folder reached the limit (seen with a 264-character scratch folder). The database had the same limit ("unable to open database file"). Model paths were not affected (see the runtime's 260-character row above). | Data folders with a long path | Diarist's own, found 16 Oct 2026; fixed in 0.1.0-beta.5 | The engine and the database get their paths in Windows' extended-length form (`\\?\`), which works at any length.
